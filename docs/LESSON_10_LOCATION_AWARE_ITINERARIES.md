# Make the itinerary use the selected place

Update: [weather-aware generation](LESSON_11_WEATHER_AWARE_ITINERARIES.md) now also
supplies eligible forecast data. The original milestone description below predates
that integration.

Previously, choosing a location affected weather lookup, but the AI still saw
only the trip's original destination text. This could make the two features plan
for different places. New itinerary generation now uses the selected place if
one exists, including its country, region, coordinates and timezone.

## Current flow

POST itinerary → load trip → read selected location once → prompt Ollama with
that geographic context → validate activities → save draft AND location snapshot.

`ItineraryService` reads `TripLocationStore` before the model call. It passes the
immutable selection to `ItineraryGenerator`, which includes `selectedLocation`
in the user-data JSON and instructs the model not to substitute a better-known
city with the same name. Only the place record goes to the model, not the trip ID,
selection timestamp or attribution metadata. Budget, currency and interests still
come from the original trip; currency is not inferred from the selected country.

When selected, `destination` in the itinerary response uses the provider's place
name. The original trip destination string itself is not updated. The full saved
`selectedLocation` includes the selected place, attribution, source and selection
time, assigned by Java rather than generated by the model.

## Why save the location in each itinerary?

Suppose you generate for Paris, France, then select Paris in the United States.
The old plan must still say which Paris was used. Saved versions contain a copy
of the selection, not a live reference to whichever location is current now.

Reading the selection only once also handles changes while generation is running:
the model prompt and returned snapshot use the same selection. Another request
may change the current location, but it cannot silently change this in-flight
plan's geographic context. No database transaction is held during generation.

## Compatibility and limits

- Without a selected location, generation continues using destination text and
  adds an explicit unverified-destination warning.
- Previously saved JSON without `selectedLocation` loads with null. We do not
  backfill it from the current selection because we cannot establish which
  location was used when that plan was generated.
- The new field fits in the existing JSONB snapshots; no migration is needed.
- Repeated POST still creates new versions; GET never regenerates a plan.
- This improves geographic context, but does not verify attraction existence,
  travel times, prices or whether the model obeyed the location instructions.
- Weather remains a separate API; it is not fetched or included in this prompt.
- No MCP or automatic tool calling is added yet.

## Try it

1. Search and save the intended location using the existing destination endpoints.
2. POST `/api/v1/trips/{tripId}/itinerary` as before.
3. Inspect `destination`, `selectedLocation` and `warnings`.
4. If you change the trip's selection later, GET an older version to see its
   original location snapshot preserved.

Tests inspect the real outgoing Spring AI HTTP payload against a fake model,
change the selection while that fake model handles the request, and confirm
the saved provenance matches the original prompt. Legacy JSON is also tested.
